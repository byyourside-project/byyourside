# Task 01 — 노트북 환경 확인 및 한국어 VAD/STT PoC

상태: 개발자 전달용 초안. 이 문서 작성 시 구현·설치·벤치마크는 수행하지 않았다.
작성일: 2026-09-28
담당: Gemini 개발자 / 검수: 사용자와 PM

## 1. 목적과 작업 경계

QCS6490 기반 발표 코파일럿을 만들기 전에 실제 테스트 노트북에서 한국어 음성을 로컬로 수집하고, Silero VAD와 SenseVoice INT8로 인식하며, 정확도·지연·누적 밀림을 측정한다. 이번 성공은 노트북 STT 단계의 성공이며 전체 코칭 품질이나 QCS6490 성능을 입증하지 않는다.

사용자가 이 지시서를 전달해 실행을 요청하면 아래 범위만 구현한다. 프로젝트 전체를 한 번에 만들거나 Task 02로 넘어가지 않는다. 저장소의 기존 사용자 변경사항을 보존한다. 먼저 적용되는 AGENTS.md와 기존 파일을 확인한다.

포함:
- OS·CPU 아키텍처·RAM·Python·마이크 환경 조사.
- 프로젝트 내부 가상환경과 최소 의존성 설정.
- 로컬 WAV 인식, 실시간 속도 WAV 재생 입력, 실제 마이크 입력.
- VAD 구간화, SenseVoice 인식, 터미널 결과 표시, 구조화 로그.
- 재현 가능한 평가와 작업 결과 문서.

제외:
- LLM 다운로드·추론·파인튜닝, 특수 토큰 추가, QNN/Genie 설치 및 변환.
- React, Spring Boot, FastAPI, DB, TTS, PPT 파서, Q&A, 영상 분석.
- 클라우드 STT 및 클라우드 LLM 호출. 런타임 대체 서비스로 Gemini를 쓰지 않는다.
- 기존 환경 전체 업그레이드, 전역 패키지 설치, 원격 배포.

## 2. 확인된 설계 전제

- 특강3 p.21의 모델은 `sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17`의 `model.int8.onnx`, `tokens.txt`이며 언어는 `ko`, provider는 CPU다. 이것을 우선 기준선으로 삼되 실제 배포 파일명을 확인한다.
- SenseVoice는 비스트리밍 인식 모델이다. VAD로 자른 구간을 순차적으로 인식하는 simulated streaming을 구현한다. 토큰 단위 네이티브 스트리밍이라고 설명하지 않는다.
- 특강의 VAD 1 thread / STT 4 threads는 출발점이다. 실제 노트북에서 확인하고 설정값을 기록한다.
- 특강의 학습용 PyTorch/DeepSpeed/CUDA 버전은 이번 추론 전용 환경에 그대로 설치하지 않는다.
- 보드용 성능을 PC 결과로 추정하여 확정하지 않는다.

## 3. 환경·모델 준비

1. 실제 실행 노트북의 OS 버전, CPU/아키텍처, RAM, Python 버전, 오디오 입력 장치와 기본 샘플레이트를 보고한다. 민감한 계정 정보나 장치 일련번호는 기록하지 않는다.
2. sherpa-onnx의 해당 OS/아키텍처 wheel 지원을 확인하고 지원되는 Python으로 프로젝트 가상환경을 만든다. 설치에 성공한 정확한 버전을 고정한다.
3. 최소 후보는 sherpa-onnx, numpy, sounddevice 및 평가·측정에 필요한 소규모 패키지다. 실제 필요한 것만 채택하고 선택 이유를 적는다.
4. 모델은 공식 sherpa-onnx 배포처 또는 사용자가 제공한 파일을 사용한다. URL, 릴리스/리비전, 파일명, 크기, SHA-256, 모델 라이선스 위치를 manifest에 기록한다. 다운로드 URL을 추측해 만들지 않는다.
5. Silero VAD와 SenseVoice의 샘플레이트 및 입력 규격을 실제 문서/설정으로 확인한다. 16 kHz mono float PCM을 기본 내부 규격으로 제안하되 모델 요구와 일치해야 한다. 장치가 48 kHz이면 실제 resampling을 수행하고 단순히 샘플레이트 숫자만 바꾸지 않는다.
6. 모델·음성·로컬 로그·가상환경은 Git에서 제외한다. 모델이 이미 있다면 다시 받지 않는다.
7. 마이크 권한이 없으면 이유와 사용자 실행 방법을 남긴다. WAV 결과로 마이크 테스트 성공을 대신 보고하지 않는다.

## 4. 구현 요구사항

### 입력과 구간화

- WAV 파일 직접 인식 모드와 실시간 속도로 PCM 프레임을 공급하는 replay 모드를 구분한다. 전자는 정확도/순수 추론 성능, 후자는 지연/큐 평가용이다.
- 마이크 콜백에서는 오디오 수집과 큐 전달만 한다. VAD/STT의 무거운 추론이나 파일 쓰기로 캡처를 막지 않는다.
- 발화 시작·끝, 마지막 발화 flush, 짧은 무음, 장시간 무음, 계속 이어지는 발화를 처리한다.
- 시작 제안값: VAD 종료 무음 0.5초, 최대 구간 4초. 실제 VAD 프레임 제약에 맞추고 값은 설정 가능하게 한다. 이 숫자는 보장된 최적값이 아니다.
- 긴 발화는 최대 구간에서 강제로 나누되 경계 손실을 평가한다. 오버랩을 쓰면 중복 텍스트를 확정 결과에 누적하지 않도록 처리·평가한다. 추가하지 않으면 경계 손실 한계를 명시한다.
- 이번 확정 텍스트만으로 시작해도 된다. 임시 텍스트를 제공한다면 partial/final과 revision을 구분한다.
- 큐는 크기를 제한하고 오래된 항목 수와 밀림 시간을 측정한다. 과부하 시 누락/폐기 여부를 반드시 기록한다. 조용히 버린 뒤 성공으로 보고하지 않는다.
- STT worker 수와 라이브러리 내부 thread 수를 구분한다. 처음에는 STT worker 하나로 기준선을 만든다.

### 로그와 시간 기준

JSONL 등에 다음 필드를 기록한다. 실제 이름은 일관되게 정하면 된다.

- run_id, segment_id, input_mode, config/model 식별자.
- audio_start_ms, audio_end_ms: 입력 오디오의 sample index 기반 구간 경계.
- endpoint_reason: silence / max_duration / end_of_input 등.
- segment_ready 시각, stt_start 시각, stt_end 시각, result_emit 시각.
- queue_wait_ms, stt_inference_ms, 텍스트, 오류/누락 상태.

프로세스 시각은 monotonic clock으로 측정하고 오디오 sample clock과 기준점을 맞춘다. 음성 내용에 없는 정확한 단어별 timestamp나 confidence를 만들어내지 않는다.

측정 정의:
- RTF = STT 계산시간 / 실제 처리 오디오 길이. 구간별 값과 합산 계산시간/합산 길이를 구분한다.
- 발화 후 지연 = 결과 출력 시각 - 실제 마지막 유성음 시각. VAD가 발화 종료를 확정한 시각부터만 재면 종료 무음 대기가 빠지므로 금지한다.
- 실제 마지막 유성음은 기준 오디오에서 수동 표시하거나 검증된 기준 annotation을 쓴다. 불가능하면 VAD 경계 기반 추정치로 명시하고 정확한 발화 후 지연과 구분한다.
- 연속 발화에서는 구간 시작부터 결과 출력까지의 시간과 강제 절단 경계부터 결과까지의 시간을 함께 기록한다. 종료 지연만 좋게 보여 주지 않는다.
- cold start 모델 로딩 시간, warm 추론 지연을 분리한다. warm-up 제외 규칙과 표본 수를 명시한다.
- p50/p95/최대값, 오류 수, 캡처 overrun, 폐기된 오디오 길이, 최대 큐 대기, 프로세스 메모리 사용량을 보고한다.

### 정확도

- 사람이 확인한 reference와 hypothesis를 같이 남긴다. 인식 결과를 정답으로 재사용하지 않는다.
- 원문과 정규화 결과를 구분한다. NFC 정규화, 공백·문장부호 처리 규칙을 고정한다.
- 한국어 CER을 주 지표로 사용한다. 숫자/영문 약어/고유명사 보존 여부는 별도 표로 확인한다.
- ITN 설정을 기록한다. `십오 퍼센트`와 `15%` 같은 표기 차이로 인한 오류와 의미 오류를 구분한다.
- 습관어가 삭제되는지 관찰한다. 이 테스트로 습관어 횟수나 실제 음절 속도가 정확히 측정된다고 주장하지 않는다.

## 5. 평가 입력

공식 한국어 sample WAV로 먼저 설치·실행을 확인한다. 이것만으로 발표 환경 검증을 완료하지 않는다.

가능하면 사용자가 직접 말한 한국어 발표 문장 30개 이상으로 평가한다. 일반 문장, 숫자·영문 약어·프로젝트명, 빠른 말과 짧은 쉼, 문장 경계 발화를 각각 포함한다. 녹음 확보가 불가능하면 측정 가능한 것만 실행하고 나머지를 NOT_RUN으로 남긴다. 합성 음성 결과는 실제 마이크 결과와 별도 표기한다.

필수 시나리오:
1. 짧은 한국어 발화와 마지막 발화 flush.
2. 60초 무음/환경 소음에서의 오인식.
3. 자연스러운 짧은 쉼을 포함하지만 종료 무음보다 긴 쉼은 없는 30초 이상 연속 발화.
4. 구간 경계에 걸친 단어의 손실과 중복.
5. 실제 마이크 10분 실행, 캡처/큐/메모리 상태 기록.
6. 모델을 준비한 뒤 외부 네트워크를 차단한 상태에서 로컬 WAV 및 가능하면 마이크 실행. 차단 방법과 확인 범위를 기록하고 시스템 네트워크 설정은 임의로 바꾸지 않는다. 사용자 조작이 필요하면 해당 항목은 대기 상태로 남긴다.

## 6. PM 검수 기준

다음은 제품 보장이 아닌 초기 목표다. 측정 후 PM이 타당성을 판단하며 개발자가 기준을 낮춰 PASS 처리하지 않는다.

| 항목 | 초기 목표 |
|---|---|
| 한국어 정확도 | 조용한 실제 발화 30개 이상에서 합산 정규화 CER 15% 이하 |
| 처리 여유 | warm 구간별 RTF p95 0.5 이하 |
| 발화 후 결과 지연 | 기준 유성음 끝에서 결과 출력까지 p95 1.5초 이하 |
| 연속 발화 | 최대 구간 4초 설정 시 구간 시작부터 결과까지 p95 5.5초 이하, 누락/중복 별도 보고 |
| 안정성 | 마이크 10분 동안 crash·캡처 overrun·무기록 폐기 없음, 큐 지연 지속 증가 없음 |
| 재현성 | 실행 절차·고정 버전·모델 manifest·원시 로그로 결과를 재계산 가능 |
| 오프라인 | 모델 준비 이후 네트워크 차단 조건의 실행 증거 |

표본 부족·마이크 미실행·annotation 부재는 NOT_RUN 또는 PARTIAL이다. 코드가 실행된다는 이유만으로 위 성능 기준을 PASS 처리하지 않는다. 기준 미달이면 실패 사례와 한 가지씩 분리한 개선안을 제시한다.

## 7. 산출물 및 보고 형식

기존 구조가 있으면 존중하되 다음 문서는 반드시 남긴다.

- `docs/reports/task_01_environment_and_stt_poc_report.md`
- `docs/reports/task_01_model_manifest.md`
- 최소 실행 코드, 의존성 고정 파일, 실행 방법, 필요한 설정.
- 재현용 테스트와 로컬 원시 측정 로그 경로. 로그·음성 자체는 기본적으로 커밋하지 않는다.

보고서는 다음 순서로 작성한다.
1. 작업 ID와 결과: PASS 후보 / PARTIAL / FAIL. 최종 승인자는 PM이다.
2. 환경, 의존성, 모델과 설정.
3. 변경 파일 목록과 각 변경 이유. Git이 있으면 기준 revision과 diff 요약.
4. 실제 실행 명령과 exit code, 로그 경로.
5. 기준별 결과 표: 목표 / 측정값 / 표본 수 / 판정 / 근거 파일.
6. 실패 사례: 정답·인식문·조건·가능한 원인.
7. 실행하지 못한 항목과 정확한 이유, 사용자 수행이 필요한 절차.
8. 보드와의 차이, 다음 단계 전 해결해야 할 사항.

실행하지 않은 결과를 추정 수치로 채우지 않는다. 외부 에이전트 환경의 측정을 사용자 노트북 결과로 표기하지 않는다. 범위 밖 작업은 제안만 남긴다. 보고서를 작성한 뒤 작업을 끝내고 PM 검수를 기다린다.
