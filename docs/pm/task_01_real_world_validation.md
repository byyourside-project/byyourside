# Task 01 — 실사용 검증 준비 및 실행

먼저 `docs/reports/task_01_revision_06_pm_review.md`를 읽는다. 요청 timeout/프로세스 회수 구현 보완을 마무리하고, 실제 한국어 발표에서 쓸 수 있는지 검증하는 단계다. Task 02 구현은 아직 시작하지 않는다.

## 이번 작업 범위

기존 STT/VAD 구조를 재작성하지 않는다. 아래 평가 도구의 최소 보완과 사용자가 바로 실행할 수 있는 안내서를 준비한다. 사용자 음성이 없으면 준비 완료까지 진행하고 실제 성능은 NOT_RUN으로 남긴다. 마이크 장시간 실행은 사용자가 녹음 준비 후 직접 시작하도록 한다. 합성 음성이나 공식 샘플로 사용자 평가를 대체하지 않는다.

### 1. 사용자 녹음 안내서

`docs/user/task_01_recording_guide.md`에 기존 `scripts/evaluate_cer.py`의 P01~P30 문장, 파일 이름, 저장 폴더, 실제 실행 명령을 적는다. 조용한 환경에서 평소 발표 속도로 녹음하며, 단어를 틀리게 읽은 경우 정답을 실제 발화에 맞게 사람이 확인한다. 평가 결과를 보고 정답을 수정하지 않는다. 원음·정답·sample rate·장치·ITN 설정·커밋·파일 해시를 manifest로 보존한다.

숫자/영문 약어 읽는 방법과 정규화 규칙을 평가 전에 고정한다. PM 기준: 문장부호 제거·공백 제거 합산 CER를 주 지표로 하고 공백 포함 CER와 숫자/전문용어별 결과를 함께 보고한다. 합산 편집거리 / 합산 정답 문자 수로 계산한다. 30개 미만은 PARTIAL이며 없는 파일을 성공 건수에 넣지 않는다. 주 지표 목표는 15% 이하이며 ITN 표기 차이는 별도 분석한다.

### 2. 평가 실행기 최소 정비

- CER 실행기는 실제 발화에 맞게 검수한 reference를 읽을 수 있게 하고, 파일 누락과 오류를 명시한다. 기존 direct STT와 VAD+STT 결과를 구분하면 절단에 따른 추가 오류를 확인할 수 있다.
- 모든 실행에 UUID/시각 등 실행별 고유 디렉터리 또는 run_id를 사용한다. rev06이라는 revision 이름만으로는 재실행 격리가 되지 않는다. 기존 결과를 덮어쓰지 않는다.
- 모델/파이프라인은 try/finally로 close한다. 예외 발생도 결과에 남긴다.
- 현재 10분 실행기의 rev3 고정 출력명을 갱신하고 실제 캡처 길이·발화 분포·부모와 자식 RSS를 포함한다. 600초 설정값만으로 600초 실측 성공이라고 판단하지 않는다. 시작에 한 문장 말하고 나머지 무음인 실행도 연속 발표 검증으로 통과시키지 않는다.
- 짧은 준비 확인 후 사용자가 10분 동안 실제 발표하도록 안내한다. 매 분 발화 분포, crash/overrun/drop, queue 대기 분포와 시간에 따른 변화, 부모/자식 메모리를 보고한다. 실패했다면 해당 실패를 먼저 분석하고 무조건 10분 반복하지 않는다.

### 3. 지연·보고 표기 정리

- `t_req_issued`는 현재 IPC 송신 직전이며 송신 완료가 아니다.
- `failure_caught_ts`는 현재 pipeline 정리 완료 후 예외 전파 직전이다. 실제 호출자 수신 시각은 테스트의 catch 이후 시각으로 별도 기록하거나 필드 설명을 고친다.
- 최초 세그먼트와 마지막 요청의 시각을 섞지 않는다. 요청별 비교 시 req_id/segment_id를 매칭한다.
- 기존 Rev05 타이밍 테스트의 상수 분해 출력은 추정으로 표시하거나 실제 계측으로 대체한다. 과거 증거는 삭제하지 않는다.
- 실제 발화 종료 후 p95 1.5초 목표를 검증하려면 사람이 원음에서 종료 sample을 표시한 표가 필요하다. 자연 종료와 hard cut을 나눠 보고하며, VAD 추정값은 estimated라고 표기한다. 사람 라벨이 없으면 해당 목표의 최종 판정은 PARTIAL이다.
- warm RTF p95 ≤ 0.5, 4초 연속 발화 구간 시작→결과 p95 ≤ 5.5초, crash/overrun/drop 0을 기존 기준으로 유지한다. 샘플 수와 실패 건수를 함께 보고한다.

### 4. 오프라인 검증 경계

현재 Python socket smoke test는 spawn/native 경로의 네트워크 차단 증거가 아니다. 사용자 장치의 네트워크 설정을 임의 변경하지 않는다. 격리 환경이나 사용자가 직접 적용·복구할 절차를 문서화하고 실제 차단 증거가 없으면 PARTIAL을 유지한다. 해당 준비 때문에 다른 녹음 안내 작업을 멈추지 않는다.

## 제출 및 종료 조건

- `docs/user/task_01_recording_guide.md`: 사용자가 무엇을 읽고 어디에 저장하고 어떤 명령을 실행하는지, 예상 시간까지 안내.
- `docs/reports/task_01_real_world_validation_report.md`: 준비 완료/실제 실행 결과를 분리하고 미실행 항목을 유지.
- 평가 도구 수정은 필요한 작은 테스트로 검증한다. 녹음 미제공 상태에서 모델 테스트 전체를 반복하거나 별도 대규모 평가 플랫폼을 만들지 않는다.
- 사용자 음성이 없으면 정확히 필요한 파일과 사용자 동작을 최종 보고하고 PM 검수를 기다린다. 실제 데이터 확보 후 측정값으로 Task 01 최종 통과를 결정한다.
