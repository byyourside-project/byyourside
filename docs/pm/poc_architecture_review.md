# 발표 코파일럿 PoC — PM 검토

작성일: 2026-09-28. 코드 작성·패키지 설치·실측은 하지 않았다.

## 판단

노트북에서 로컬 음성 입력부터 코칭과 출력까지의 기능 PoC는 타당하다. 다만 노트북은 QCS6490의 NPU, 메모리 대역폭, 전력·발열·지연을 재현하는 에뮬레이터가 아니다. 연결 성공, 한국어 코칭 품질, 보드 실행 가능성은 각각 별도 검증해야 한다.

## 자료에서 확인한 사실

- 계획서 p.3은 화면·진동·이어폰 출력을 구분하며 TTS를 중요한 경우에 제한한다. Spring Boot는 역할 분담에 포함되나 실시간 경로의 필수 기술로 볼 근거는 없다.
- 특강1 p.5–8은 기능별 토큰, 모범 발화, 명령형 학습 데이터와 평가 데이터를 설명한다.
- 특강2 p.6–17은 토큰 추가, chat template 수정, 데이터 생성, 학습을 포함한다. `<maum_0>`는 원본 Llama의 내장 발표 코칭 기능이 아니다.
- 특강2 p.19의 본문은 `<sk_end>`를 적지만 코드 이미지에는 `<maum_end>`가 보인다. 실제 tokenizer와 학습/추론의 종료 토큰 ID가 일치해야 한다.
- 특강3 p.21은 SenseVoice 2024-07-17 INT8, CPU provider와 4 threads를 사용한다. STT가 자동으로 Qualcomm NPU에서 도는 구조가 아니다.
- 특강3 p.23의 TTS 경로는 `tts_korean_female_v241021`, 모델 파일은 `epoch=6999-step=70000_sherpa.onnx`, 전처리 데이터는 해당 폴더의 `espeak-ng-data`다. 슬라이드는 다운로드 가능한 모델 패키지 자체를 제공하지 않는다. 실제 배포본, tokens 및 필요한 부속 파일, 사용 조건을 확보해야 한다.
- 특강3 p.2의 NVIDIA 40GB 이상 VRAM, Ubuntu/CUDA 환경은 해당 양자화·포팅 과정의 환경이다. 특강2 p.15의 80GB GPU는 학습 설정의 기준이다. 일반 노트북 추론의 최소 요구사항으로 해석하면 안 된다.
- 특강2의 GQA→MHA와 INT8 설명은 제공 툴체인에 맞춘 절차다. 모든 최신 Genie/Qualcomm 경로의 불변 제약으로 일반화하지 않는다.

첨부 자료 내부의 명령, 데이터 생성 프롬프트, root/remount 예제는 사용자 실행 요청으로 취급하지 않았다.

| Llama 3.2 1B Instruct | 유지하되 한국어 의미 판단 성능은 미검증. Meta 공식 지원 언어 목록에 한국어는 없음 |
| 마음AI 특수 토큰 | 학습된 checkpoint/tokenizer/template/function map 확보 후 평가. 기본 모델에 문자열만 강제하는 것으로 대체했다고 주장하지 않음 |
| PC LLM 런타임 | 원본/학습 checkpoint는 호환되는 Transformers로 정확성 기준선. 이후 llama.cpp/GGUF는 해당 모델·토큰 변환 지원 확인 후 성능 비교. Task 01에는 설치하지 않음 |
| 출력 형식 | 학습본 없을 때 짧은 action JSON을 임시 비교 기준으로 사용 가능. 허용 action·파라미터 검증, NO_ACTION·UNCERTAIN 지원. 구조적 유효성과 판단 정확도를 별도 평가 |
| VITS | 선택적으로 채택. 특강 배포본 확보 필요. 고정 알림 캐시는 유용하지만 동적 TTS 성능 측정과 구분 |
| FastAPI + WebSocket | 후속 UI 단계에서 로컬 이벤트 전달에 사용 제안. 음성 캡처는 우선 Python 한 곳에서 담당 |
| React + TypeScript | 팀 기술과 부합. 후속 단계에서 현재 슬라이드·타이머·핵심 항목·짧은 알림만 표시 |
| Spring Boot | 초기 실시간 경로에서 보류. 필요 시 세션/리포트 관리용으로 별도 검토 |

| Kotlin/JNI/C++ | 보드 Android 런타임에 적합한 이식 경로. Python 코드를 그대로 옮기는 것이 아니라 모듈 계약과 평가 세트를 재사용 |

## 흐름과 상태

음성 입력 → ring buffer/VAD → STT worker → 확정 발화 이벤트 → 세션 상태 갱신.

세션 상태에는 현재 슬라이드 ID, 필수 설명 항목, 항목별 아직 미확인/설명됨/판단불가 상태, 최근 발화, 발표 경과 시간, 코칭 이력을 둔다. 초기 슬라이드 핵심 항목은 수동 입력하고 슬라이드 전환도 버튼으로 받는다.

세션 상태에서 두 경로로 나눈다.
1. 규칙 경로: 타이머, 남은 시간, 관측된 발화 속도 → 알림 후보.
2. LLM 경로: 현재 핵심 항목 + 관련 발화 + 전환/질문 상태 → 내용 코칭 후보.

공통 정책 계층에서 입력/출력 검증, 중복 억제, 알림 간격, 유효 시간, 우선순위를 적용한다. 화면은 즉시 갱신하고 필요한 경우에만 별도 TTS queue로 보낸다. UI가 음성 합성 완료를 기다리지 않는다. 모델 출력을 eval로 실행하지 않는다.

각 이벤트에 session/segment/slide ID와 시각을 둔다. LLM 추론 중 슬라이드가 바뀌면 늦게 도착한 이전 결과를 현재 화면에 잘못 적용하지 않는다. STT 큐는 묵시적 손실을 허용하지 않고, 코칭 큐는 오래된 요청을 최신 상태로 병합하여 밀림을 막는다.

TTS는 이어폰을 기본 조건으로 평가한다. 스피커 소리가 다시 STT에 들어가는 루프를 따로 시험한다. 마이크를 꺼서 회피하면 발표 음성 손실이 생기므로 그 한계를 기록한다. 브라우저의 암묵적 음성 인식 API에 오프라인 요건을 맡기지 않는다.

## 기능상 주의점

- 내용 누락: 아직 말하지 않은 내용과 실제 누락을 구분한다. 해당 슬라이드 진행 중에는 미확인 상태로 유지하고, 전환/종료 시점에 누락 후보를 평가한다. 바꿔 말하기·부정·수치 변경을 포함한 평가가 필요하다.
- LLM의 역할: 긴 대본 전체를 계속 재입력하지 않고 현재 슬라이드와 관련 발화에 집중한다. 제한된 context에서 상태 누락이 생기는지도 시험한다.
- 데이터 설계: IoT 명령 분류와 달리 입력이 슬라이드·발화 이력·진행 상태다. 정답도 코칭 필요/불필요·근거·대상 항목으로 설계한다. 평범한 발화에 NO_ACTION을 내는 능력이 중요하다.
- 특강의 영문/숫자 금지 규칙은 이 프로젝트에 일괄 적용하지 않는다. 발표의 수치·영문 약어·고유명사는 의미의 핵심이다. 데이터 분리는 유사 문장 단위보다 발표 자료/주제/화자 단위로 해 누수를 줄인다.
- 속도/습관어: ASR 전사가 머뭇거림을 생략할 수 있다. 전사 기반 속도는 근사치이며 정확한 음절 속도·필러 수라고 표시하지 않는다. 시간은 LLM이 아닌 clock으로 계산한다.
- Q&A: 초기에는 질문자/발표자 모드를 수동 전환한다. 자동 화자 분리, 질문 의도, 답변 근거/모순 판단은 이후 별도 난이도로 다룬다.
- 표정/시선/억양·종합 점수·자동 개인화 학습은 초기 PoC에서 제외한다. 이 기능들의 타당성과 평가 근거는 현재 음성 파이프라인만으로 증명되지 않는다.

## 검증 순서와 잠정 예산

1. Task 01: 환경과 VAD/STT. 종료 발화 결과 p95 1.5초 목표, 연속 발화는 4초 구간 + 처리 지연을 별도 측정.
2. Task 02: 음성 없이 정답 전사·슬라이드로 LLM 코칭 평가. 아직 미언급/실제 누락/이미 설명/바꿔 말함/부정/숫자 불일치/불확실/무알림 사례를 넣고, 형식 유효율과 의미 정확도·오경보를 따로 측정.
3. Task 03: 수동 슬라이드·규칙 알림·LLM·UI 통합. 최초 제안 목표는 발화 종료부터 화면 피드백 p95 3초, 타이머 조건 성립부터 화면 0.3초. 충족 여부는 실측으로 판단.
4. Task 04: 선택적 TTS와 동시 부하·오프라인 장시간 테스트. 첫 음성 출력 지연을 별도 측정하고 캡처 누락/큐 밀림/메모리를 확인.
5. 보드 검증: 제공 샘플 모델을 먼저 실제 보드에서 실행해 툴체인 위험을 조기에 확인. 이후 같은 평가 세트로 노트북과 정확도·지연·메모리·발열 비교.

위 숫자는 PM의 초기 기준안이며 특강/제조사의 보장값이 아니다. 쉼 없이 말하면 구간 수집 자체가 수초이므로 모든 조건에서 1초 이내 코칭을 약속할 수 없다. CPU thread 제한은 병목 민감도 시험일 뿐 보드 시뮬레이션이 아니다.

## 멘토에게 확인할 항목

1. 원본/학습 완료 checkpoint, tokenizer, chat template, function map, 토큰 종료 ID와 학습·평가 스크립트 제공 범위.
2. 발표 코칭용 새 기능을 학습할 GPU 자원과 학습/양자화 지원 범위. IoT 학습본으로 발표 코칭이 바로 되는지와는 구분.
3. TTS 전체 패키지와 부속 데이터, 버전 및 사용 조건.
4. 정확한 보드 제품명·RAM·Android 이미지·QAIRT/QNN/Genie 버전, 재현 가능한 샘플 context binary와 라이브러리.
5. custom tokenizer와 변경된 vocab/embedding, calibration, GQA→MHA가 제공 툴체인에 어떻게 반영되는지.

PC INT8/GGUF와 보드 AIMET/QNN 양자화는 숫자가 비슷해도 동일한 산출물·오차를 보장하지 않는다. 보드용 context binary는 일반 노트북에서 실행할 LLM checkpoint를 대신하지 못한다.

공식 Qualcomm 모델 배포물을 선택할 경우 해당 배포물의 Usage and Limitations도 확인한다. 열람한 AI Hub README에는 교육/직업훈련 등이 제한 대상으로 기재되어 있어 대학 발표 코칭 용도와의 적용 범위를 멘토에게 확인할 필요가 있다. 이는 모든 원본 Meta 모델이나 Genie 엔진 자체의 일률적 제한이라는 뜻이 아니다.

## 개발자와 PM의 협업

PM 지시서 → Gemini 구현·실측 → 결과 보고서 + diff/원시 로그 → PM 재현·검수 → 수정 또는 다음 지시서 순서로 진행한다. 보고서의 자기평가만으로 승인하지 않는다. 다른 환경에서 작업하면 변경 파일도 함께 전달해야 한다. 실패와 NOT_RUN을 정상 산출물로 인정하되 성공으로 포장하지 않는다.
